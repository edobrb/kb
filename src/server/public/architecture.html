System architecture

How a wiki page becomes a cited answer.

Three sources are gathered into a folder of markdown, cut into self-describing chunks, indexed twice (dense vectors and BM25), and fused at question time. Everything runs on this machine: Ollama for the models, LanceDB for the vectors, a gzipped JSON file for the keyword index. Numbers on this page are read live from the running index.

01 The pipeline

Two lanes, one index.

The offline lane runs on demand (npm run sync, npm run ingest) and is incremental at every step. The online lane answers a question in a few seconds and only ever reads. Click a stage to see what it does, what it reads and writes, and where the code lives.

02 What is indexed

Documentation, contracts and cards. Not code, not meeting notes.

The knowledge base exists to answer technical questions about OnePlatform and TeamSystem. That goal decides the scope: TechDocs pages, ADRs, in-repo documentation, API contracts and one card per repository. Generated API reference (~6 200 of 8 600 portal pages), source code (~90 % of the files) and sprint ceremonies are filtered out before they ever reach the index. 03 Anatomy of a chunk

Every chunk says where it comes from.

The chunker parses markdown into blocks (headings, fenced code, tables, paragraphs), tracks the heading stack and packs blocks to about 450 tokens (never over 700), preferring to break at headings once a chunk has at least a third of the target. The text that gets embedded and BM25-indexed is heading path ⏎⏎ content, where the heading path starts with the breadcrumb written by sync. “Decision” alone means nothing. GitLab › oneplatform/adrs > ADR0010 Client Credentials > Decision does.

04 Anatomy of a query

Two rankings, one fusion.

Embeddings understand paraphrase (“come si ottiene un token machine-to-machine” ≈ “M2M client credentials”) but are weak on exact identifiers. BM25 nails ADR0016, TSPAY, X-Correlation-Id but knows no synonyms. Each returns 24 candidates; Reciprocal Rank Fusion merges them without calibrating scores, binding documents get a nudge, at most 3 chunks per document survive, and 6 reach the model. The probe below runs the real retriever and breaks each result’s score into its two contributions.

score(chunk) = ( wvec / (60 + rankvec) + wbm25 / (60 + rankbm25) ) × boost(authority)    w = 1.0 · boost: binding 1.15, normative 1.12, else 1.0
What does ADR0010 say about client credentials? Come funziona il social login in TSID? OnePlatform data store tiers RFC 9457 error format
Runs POST /api/search with topK: 10. Vector rank and BM25 rank are the positions in each list before fusion; a dash means the chunk was only found by the other index.
vector contribution 1/(60+rank)BM25 contribution 1/(60+rank)

The BM25 tokenizer, live

NFKD accent folding (perché → perche), lower-casing, letters and digits only, Italian and English stopwords dropped, tokens under two characters dropped. Alphanumeric codes are also split (dashed boxes) so ADR0010, ADR 0010 and adr-0010 all match. Okapi BM25 with k1 = 1.2, b = 0.75. Same function as src/store/bm25.ts.

What the model receives

The system prompt carries the rules (answer only from context, cite [n] after each claim, prefer binding sources on conflict, name repository and file when answering from a repository document, reply in the user’s language) followed by the numbered context blocks:
[1] GitLab › oneplatform/adrs > ADR0010 Client Credentials > Decision
source_type=adr kind=doc authority=binding url=https://biosphere…/ADR0010.md
Use the OAuth 2.0 client credentials grant issued by TS ID…

-----

[2] Dev Portal › TS ID > Machine to machine > Token request
source_type=devportal kind=doc authority=descriptive url=https://development…
POST /oauth2/token with grant_type=client_credentials…
Then the last 6 turns of history and the new question. Generation streams from Ollama /api/chat with two kinds of delta, thinking and content, forwarded as separate SSE events. After the stream ends the [n] actually cited are extracted so the UI can dim unused sources. A follow-up question is first rewritten into a standalone query from the last 4 turns (temperature 0, no thinking).

05 What triggers re-work

Nothing is redone unless its key changed.

Every stage has its own change-detection key. A sync that finds nothing new rewrites no file, so the next ingest has nothing to embed. An unchanged repository costs one branch request, an unchanged portal entity one metadata request, an unchanged space one paginated listing.

06 Storage and API

Files on disk, no services to run.

LanceDB data/lancedb/

One chunks table, embedded and file-based (Apache Arrow columns). Filters are SQL-like predicates such as kind IN ('api'). No ANN index: a brute-force cosine scan is exact and takes milliseconds at this scale.

idsource_idsource_typekindtitlesource_urlauthoritylanglast_modifiedrel_pathordinalheading_pathcontenttextline_startline_endvector float32[…]

BM25 data/bm25.json.gz

Okapi BM25 postings (term → [docIdx, tf, …]) with per-chunk lengths and filter columns, gzipped. Rebuilt from the LanceDB table after every ingest, so the two indexes cannot drift.

idslenssourceTypeskindsauthoritieslangspostings

Manifest data/manifest.json

What is indexed: per source id the content hash, chunk count and indexing time, plus the embedding model, dimensions and chunk sizes the index was built with. Written at most every 5 s during ingest, which is what makes an interrupted run resumable.

embeddingModelembeddingDimensionschunkingdocs[source_id]

Sync state data/sync/<source>.json

Per-source item fingerprints and connector memory: portal coveredRepos and repoEntities, GitLab projectHeads and projectEnrichment, Confluence space counts.

itemsmetalastRunAt

Map data/kb-map.json.gz

Built by npm run map: every vector random-projected to 256 dims, UMAP to 2-D, k-means clusters named by distinctive terms. Parallel arrays, dictionary-encoded strings, no chunk text: the browser fetches passages on demand.

documentsclusterspoints{x,y,doc,ord,head,cl}labels
